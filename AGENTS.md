# AGENTS.md — Инструкция и правила разработки ядра

Файл содержит фундаментальные правила проекта, обязательные для выполнения агентами и контрибьюторами в каждом запросе. Документ является живым: дополняйте его новыми правилами и соглашениями по мере эволюции архитектуры.

---

## 1. Главные инженерные принципы
1. **Parity-First (100% ванильный паритет):** Любое изменение, нарушающее хотя бы одну ванильную механику (порядок тиков, редстоун, ИИ и тайминги мобов, спавн, воронки, update suppression), **считается багом и отклоняется**. Оптимизации только алгоритмические ($O(N) \to O(1)$, кэширование, safe off-thread).
2. **Data-Driven (доказательная оптимизация):** Никаких изменений «на глаз».
   * Сначала замер базовой линии (Baseline MSPT + Flamegraph).
   * Выявление узкого места (Hotspot).
   * Применение патча и повторный замер (Proof of Improvement).
3. **Атомарность патчей:** Один патч — одна изолированная оптимизация или подсистема с понятным описанием в заголовке патча.

## 2. GitHub & Git Workflow (Public Repository)

### 2.1. Ветки (Branching Strategy)
* `main` — стабильная кодовая база, всегда компилируется и проходит тесты.
* `opt/<name>` — ветки для конкретных оптимизаций (напр., `opt/spatial-hopper-search`).
* `feat/<name>` — новая инфраструктура (тулчейн, бенчмарк, утилиты).
* `fix/<name>` — исправление багов паритета или сборок.

### 2.2. Формат коммитов (Conventional Commits)
* `opt(subsystem): описание оптимизации` (напр., `opt(hopper): replace entity scan with spatial hash grid`)
* `perf(benchmark): улучшение сценариев тестирования`
* `fix(parity): исправление отклонения от ванильного поведения`
* `feat(build): добавление задач в gradle/тулчейн`
* `docs: обновление документации или спецификаций`

### 2.3. Стандарт Pull Request (PR)
Любой PR с оптимизацией обязан содержать:
1. **Суть изменения:** какую проблему решаем и каким алгоритмом.
2. **Доказательства производительности:**
   * Baseline MSPT $\to$ New MSPT (на тестовом стенде).
   * Скриншот или ссылки на Flamegraph до/после.
3. **Чеклист паритета:** подтверждение, что проверены релевантные ванильные механики.

### 2.4. Issue Labels
* `performance` — подтвержденные узкие места CPU/памяти.
* `parity-bug` — критический приоритет: обнаружено расхождение с ванилью Mojang.
* `benchmark` — вопросы и задачи по нагрузочному стенду.
* `upstream` — изменения, связанные с новыми версиями Minecraft.

## 3. Правила работы с кодом и патчами
* **Не трогать сгенерированные файлы напрямую:** Исходники NMS в рабочей папке модифицируются только через механизм патчинга.
* **Использовать официальные маппинги (Mojmap):** Никаких обфусцированных имён (`a`, `b`, `c`) в патчах.
* **Zero Allocations в горячих циклах:** Избегать создания временных объектов (`BlockPos`, `Vec3`, `new ArrayList`) внутри методов, вызываемых каждый тик для сотен мобов/блоков.
