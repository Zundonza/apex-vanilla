# Дизайн-документ: Vanilla-First Custom Minecraft Server Core & Benchmark Harness

**Дата:** 2026-10-27  
**Статус:** Согласовано  
**Целевая платформа:** Minecraft 1.21.x, Java 21, официальные маппинги Mojang (Mojmap)  
**Ключевая цель:** 100% сохранение всех ванильных механик («Parity-First») при достижении 20 TPS в тяжёлых условиях за счёт алгоритмической оптимизации и доказательного профилирования.

---

## 1. Контекст и архитектурные цели

Традиционные оптимизированные серверные ядра (Paper, Purpur) достигают производительности за счёт компромиссов в игровой механике:
- Entity Activation Range (пропуск тиков ИИ сущностей);
- Альтернативные движки редстоуна (Alternate Current / EigenCraft), меняющие порядок апдейтов;
- Изменённая логика воронок (Hopper cooldowns / batching);
- Подавление обновления блоков (отключение vanilla update suppression);
- Изменение правил спавна и слияние сущностей.

На ролеплей- и технических серверах эти изменения приводят к поломке сложных ферм, сортировочных систем, систем жителей и редстоун-компьютеров.

### Принципы Parity-First ядра
1. **Строгая детерминированность:** Порядок тиков, фазы обновления мира, логика спавна и распространение редстоун-сигналов полностью идентичны официальному ванильному серверу Mojang.
2. **Алгоритмические оптимизации:** Ускорение достигается не урезанием вычислений, а заменой структур данных ($O(N^2) \to O(1)$), пространственным хэшированием (Spatial Partitioning), кэшированием воксельных коллизий (`VoxelShape`) и POI жителей.
3. **Безопасная асинхронность:** Вынос в отдельные потоки исключительно тех операций, которые не влияют на состояние тика (сериализация сетевых пакетов, сжатие чанков, дисковый I/O).
4. **Data-Driven подход:** Никаких слепых оптимизаций. Каждое изменение опирается на предварительный замер baseline, анализ Flamegraph, подтверждённое снижение MSPT (миллисекунд на тик) и проверку паритета.

## 2. Структура проекта и сборочный пайплайн (Build & Toolchain)

Проект организуется как автономное монолитное ядро на базе патчей официального сервера Mojang.

### Структура репозитория
```text
/
├── .git/
├── docs/
│   └── superpowers/
│       └── specs/
│           └── 2026-10-27-vanilla-core-benchmark-harness-design.md
├── build.gradle.kts
├── settings.gradle.kts
├── gradle/
│   └── wrapper/
├── patches/                   # Git-патчи изменений в NMS (net.minecraft.server)
├── benchmark/                 # Инфраструктура автоматических замеров
│   ├── run.py                 # Runner сценария тестирования
│   ├── world-template/        # Эталонный полигон («пыточный мир»)
│   └── reports/               # Сгенерированные отчеты и Flamegraph
└── run/                       # Рабочая директория сервера для локальных тестов
    ├── server.properties
    └── eula.txt
```

### Пайплайн сборки и патчинга
- **Gradle 8.x + Java 21 Toolchain**:
  - `applyPatches`: Загружает официальный `server.jar` Mojang для целевой версии 1.21.x, деобфусцирует его с официальными маппингами Mojmap, форматирует исходный код и накладывает патчи из директории `patches/` в рабочий каталог `work/Minecraft/`.
  - `rebuildPatches`: Сравнивает изменения в `work/Minecraft/` с оригинальным исходным кодом и перегенерирует атомарные `.patch` файлы в папку `patches/`.
  - `createReobfBundlerJar`: Компилирует пропатченный код в автономный монолитный JAR-файл `server.jar`, готовый к запуску через `java -jar server.jar`.

## 3. Дизайн тестового полигона («Пыточный мир»)

Для создания воспроизводимой стрессовой нагрузки создается детерминированный мир `world-template` с 4 изолированными секторами в чанках с принудительной прогрузкой (`/forceload`).

### Сектор 1: «Торговый мегаполис» (Нагрузка на ИИ мобов и Brain/POI)
- **Состав:** 250 жителей в индивидуальных кабинках 1×1 с рабочими местами (кафедры, компостеры) и кроватями.
- **Точки нагрузки:**
  - `Villager.tickBrain()`: постоянная работа дерева поведений;
  - `PoiManager`: запросы поиска и верификации рабочих мест;
  - `PathNavigation`: попытки расчета путей в замкнутых пространствах;
  - Обмен данными о репутации и сплетнях (`GossipContainer`).

### Сектор 2: «Логистический узел» (Нагрузка на инвентари и воронки)
- **Состав:** Кластер из 1200 взаимосвязанных воронок с закольцованной передачей предметов через двойные сундуки.
- **Точки нагрузки:**
  - 600 открытых сверху воронок, непрерывно сканирующих AABB-пространство над собой (`EntitySearch` / `findEntities`);
  - 600 закрытых/заблокированных воронок;
  - `HopperBlockEntity.tryMoveItems()`: проверки перемещения предметов и пересчет сигналов компаратора.

### Сектор 3: «Индустриальный редстоун» (Обновления блоков и расчет освещения)
- **Состав:**
  - Высокочастотные 1-tick и 2-tick клоки на компараторах и наблюдателях (observers);
  - Змейка из редстоун-пыли длиной 120+ блоков, циклическое затухание от 15 до 0;
  - Массив поршней, толкающих подвижные блоки (смена вокселей и коллизий).
- **Точки нагрузки:**
  - `RedstoneWireBlock.updatePowerStrength()` / `NeighborUpdater`: лавинообразные обновления блоков;
  - `LightEngine`: динамический пересчет блочного света при срабатывании редстоун-ламп.

### Сектор 4: «Коллизионный ад» (Нагрузка на физику и VoxelShape)
- **Состав:** 180 коров и куриц в замкнутом пространстве 2×2 блока с проточной водой.
- **Точки нагрузки:**
  - `Entity.pushEntities()`: квадратичный рост взаимного отталкивания мобов ($O(N^2)$ без пространственного хэширования);
  - `VoxelShape.join()`: постоянные проверки пересечения хитбоксов с углами блоков.

### Условия изоляции полигона
- Погода зафиксирована: `doWeatherCycle = false`.
- Время суток зафиксировано: `doDaylightCycle = false`.
- Чанки зафиксированы через `/forceload add`.
- Спавн естественных мобов отключен: `doMobSpawning = false` (нагрузка создается только целевыми мобами стенда).

## 4. Инфраструктура профилирования и сбора метрик

### Измеряемые показатели
1. **MSPT (Milliseconds Per Tick):**
   - Средний MSPT за окно измерения (1000 тиков).
   - 95-й перцентиль (P95 MSPT) и 99-й перцентиль (P99 MSPT) для выявления микрофризов.
   - Эквивалентный TPS: $\min(20.0, 1000.0 / \text{MSPT})$.
2. **Аллокация памяти (Allocation Rate) и GC:**
   - Скорость создания объектов в куче (МБ/сек).
   - Частота и длительность пауз сборщика мусора (G1 GC).
3. **CPU Flamegraph (Пламенные диаграммы):**
   - Доля процессорного времени, приходящаяся на NMS-методы.

### Архитектура скрипта бенчмарка (`benchmark/run.py`)
1. **Reset:** Очистка `run/world` и распаковка чистого эталона из `benchmark/world-template`.
2. **Warmup Phase:** Запуск сервера с JVM 21, ожидание 250 тиков для прогрева JIT-компилятора (C2 JIT tier 4 compilation).
3. **Measurement Phase:** Запуск `async-profiler` через Java Agent на 1000 тиков с флагами сбора CPU и Allocation событий.
4. **Shutdown & Artifacts:** Корректный `/stop`, сбор логов, генерация `flamegraph-cpu.html`, `flamegraph-alloc.html` и сохранение метрик в `benchmark/reports/<timestamp>-<name>.json`.

## 5. Протокол оптимизации и верификации паритета

Каждый цикл оптимизации подчиняется строгому алгоритму:
1. **Baseline Замер:** Запуск бенчмарка на чистом ванильном ядре. Фиксация точки отсчета ($T_{\text{base}}$ MSPT, топ-1 горячий метод).
2. **Проектирование патча:** Разработка алгоритмической замены (например, spatial hashing для `findEntities` в воронках).
3. **Контроль паритета:**
   - Поведение мобов и ферм в точности соответствует ванильному.
   - Никаких задержек, пропусков или измененных состояний.
4. **Тестовый Замер:** Запуск бенчмарка с патчем.
5. **Валидация:**
   - Если MSPT снизился и поведение не нарушено $\to$ патч фиксируется (`rebuildPatches`, `git commit`).
   - Если MSPT не изменился или нарушился паритет $\to$ откат.
